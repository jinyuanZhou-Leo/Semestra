<!-- ⚠️ Once this folder changes, update me. -->

Backend exposes FastAPI endpoints and coordinates auth, CRUD, and domain logic.
Data contracts are defined in Pydantic schemas and persisted through SQLAlchemy models, with Alembic now owning schema evolution instead of startup-time compatibility rewrites.
Auth now signs JWTs from env-backed secrets, ships browser sessions via HttpOnly cookies, requires CSRF headers for cookie-authenticated write requests, revokes issued JWTs by bumping a persisted user session version on logout, validates bearer tokens server-side with an explicit access-token type boundary so email-verification JWTs cannot authenticate API reads or writes, and supports Resend-backed email verification codes for registration, email-code login, and password resets through persisted verification challenges plus one-time verification tokens. Register, login, and reset delivery stay bound to purpose-specific Resend templates, email identities remain case-insensitive across password, email-code, and Google sign-in paths, public auth now also supports an email-driven `continue` entry that sends a login code for existing accounts or a registration code for new emails without revealing the branch until the code is verified, the old direct `/auth/register` bypass is gone, current-user reads now derive `active_program_id` without committing a write or tripping SQLAlchemy cross-session ownership errors, and the irreversible account-deletion path still clears owned academic data, auth metadata, and stored course-resource files.
Program-level subject-code color maps now persist in the backend as stable locked assignments so Course List, Program Dashboard, Course Settings, Todo, and backups share the same automatic/default course colors while new subject codes avoid collisions when palette room remains.
Course resources now store file metadata in SQLite, file bytes on local disk, saved external URLs as link-only records, enforce a 50MB account-wide quota across every course resource upload, and delete saved links without touching the storage root.
LMS integrations now persist multiple encrypted provider-neutral connections per user, let each Program choose one active integration, and attach Courses to LMS data through dedicated link rows rather than overloading the local Course entity; batch LMS course import is now whole-request atomic, so any course-import failure rolls back the full batch instead of leaving partial local Course or link rows behind.
The backend now exposes generic LMS course import, Course link/relink/unlink, ICS-backed course imports, and read-only Navigation, Announcement, Module summary, Module item, Assignment, Grade, Page, Quiz, Syllabus, File metadata/download, and Calendar APIs without leaking secrets; semester LMS calendar reads now degrade to an empty list when a Program has no LMS configured, while Calendar-facing semester schedule reads now use a dedicated date-range endpoint instead of one-request-per-week fan-out, with Canvas implemented through a REST adapter that owns provider-specific config normalization, outbound SSRF hardening, centralized request/file-stream constants, credential masking, normalized module-item target metadata, inline module-summary item titles for the main modules payload, and safe file proxy/download handling before data reaches shared LMS consumers.
Account backup import/export now restores current persisted features end to end, including LMS integrations plus course links, Program-level unassigned courses, unassigned-Course plugin activations, semester date windows and Reading Week, course schedule structures, semester todo state, course resources with file bytes, gradebook LMS provenance plus optional point-based assessment inputs, and background plugin preload preferences, while the heavy backup serialization/restore flow now lives in a dedicated transfer module instead of bloating the FastAPI entrypoint.
The backend API layer is now split across focused router/support modules so `main.py` stays below 1k lines: auth or user or LMS or backup routes, schedule or event routes, widget or tab routes, shared API validators, schedule helper logic, and CRUD slices each live in dedicated files, while the slimmer entrypoint now disables OpenAPI/docs in production, enforces a Host allowlist, bounds resource-upload reads before the remaining course import and resource routes persist file data, routes ICS imports plus detail-response assembly through small private helpers instead of route-local orchestration blocks, logs unexpected upload storage failures through the standard logger instead of stdout prints, and now fails fast on schema drift instead of surfacing late 500s from partially migrated SQLite databases.
Program-level plugin management now persists installed plugins separately from Semester enablement, exposes dedicated Program/Semester/Course plugin APIs, and now stores explicit `is_enabled` flags at the Program-installation, Semester-activation, and unassigned-Course-activation layers so disable preserves plugin data while delete still removes it; public plugin identity plus `tabs`/`widgets`/`settings.panels` metadata now come from generated backend manifests under `backend/generated/plugin-manifests/*.plugin.json` plus optional `*.setup.schema.json`, emitted from typed frontend `frontend/src/plugins/*/plugin.ts` authoring entries, while private builtin/host-shell kind and visibility rules come from `frontend/src/plugins/host-policy.json`. Plugin System V2 now additionally treats `builtin-dashboard` and `builtin-setting` as host-shell tabs instead of public plugins, derives host-shell default installation and locking from host policy instead of plugin-authored fields, persists `tab_settings` plus `workspace_tab_order_entries`, backfills legacy Program installation settings into Program-scoped tab settings, preserves assigned-course tab overrides as course-scoped rows during migration, removes the historical `program_settings` and `semester_overrides` columns now that inherited plugin settings flow only through `tab_settings`, self-heals duplicate or divergent legacy assigned-course tab rows while computing a shared semester course-tab order for dirty local SQLite databases, drops the obsolete Semester/Course `plugin_settings` table, rejects runtime-tab settings writes for missing tabs before persisting, fails fast when two plugins declare the same tab or widget type, and now returns per-key tab-setting inheritance metadata (`scope_settings`, `inherited_settings`, `setting_sources`) so Program/Semester/Course settings UIs can explain the effective layer and reset a key back to the nearest inherited value. Runtime payload assembly stays isolated in a dedicated helper module instead of living inside `main.py`.
Semester plugin setup is now sourced from descriptor-backed setup schemas that the backend loads directly from generated manifests into explicit `/plugin-system/...` APIs for setup definition/state/save/review semantics instead of overloading the generic activation update route. Setup fields now declare their owning `settings_key`, setup writes are projected straight into semester-scoped `tab_settings` rows keyed by that generic bucket id, and review reads those resolved settings back as the final setup state instead of maintaining a separate validated `setup_state` payload. Semester plugin activation reads now also serialize the full Program-enabled plugin set for settings pages, returning non-imported Semester plugins as off-state rows while Course inheritance still filters down to enabled plugins only.
Builtin event-type definitions now live only inside builtin-event-core `tab_settings` payloads; the backend no longer persists or constrains a separate `course_event_types` table, so schedule validation, ICS import, backup import/export, and plugin-owned cleanup all resolve event types through settings-backed helpers.
Semester creation now supports a resumable draft-first wizard lifecycle: draft rows live in `semesters` via `lifecycle_state`, `creation_step`, `draft_updated_at`, and `review_ready`, dedicated draft routes handle resume, review, finalize, and discard flows, plugin activations serialize setup summaries plus per-plugin review errors, draft creation now initializes only plugin activations plus the default `course-list` widget transactionally, and a partial unique index now enforces one in-progress draft per Program even under concurrent requests. The wizard plugin-management flow now also provides a bulk activation update endpoint that applies one transactional enable/disable operation across many plugins and returns the updated draft payload instead of forcing the client to fan out per-plugin writes. Backend reads now only normalize legacy `dashboard`/`settings`/`builtin-settings` tab rows across Semester and Course workspaces so stale data cannot duplicate the frontend-derived shell tabs.
Course-scoped widget/tab ownership checks now resolve through `Course -> Program` directly so Program-level courses without a bound semester still support Course homepage initialization and tab/widget CRUD, while course create or update now rejects cross-Program semester assignment, and course update or delete now executes stat or draft-touch side effects in a single transaction instead of partial-commit steps. Local backend development can now also be entered from the repository root through `npm run dev:backend`, which delegates to `uv run uvicorn` inside this folder.
